# Grant Aerona3 Home Assistant Integration

Unofficial HACS integration for Grant Aerona3 air-source heat pumps, talking Modbus over serial/TCP. Solo-maintained, no CI — validation is manual (see `.claude/skills/validate`).

## Feature-gating architecture

Users only get entities for hardware they actually own (an unfiltered install creates 150+ entities). Don't add a new register or entity without wiring it into this system:

- Feature keys live in `const.py`: `has_dhw_tank`, `has_buffer`, `has_ehs`, `has_cooling`, `zones` (`"single"`/`"dual"`, exposed internally as the pseudo-feature `zone2`). `DEFAULT_FEATURES` turns everything ON — this is required so existing config entries keep all their entities after an upgrade; don't change these defaults for backward-compat reasons even though a fresh UK install would prefer heating-only/no-DHW defaults (that's handled in the config flow, not here).
- Register gating is data-driven: `INPUT_REGISTER_FEATURES`, `HOLDING_REGISTER_FEATURES`, `COIL_REGISTER_FEATURES` in `const.py` map register ID → tuple of required feature keys (AND semantics — e.g. Zone 2 cooling needs both `has_cooling` and `zone2`). A register absent from its map is core and always enabled/polled.
- `features.py` holds the helpers: `get_feature(entry, key, default)` (options flow value wins over the original data), `enabled_features(entry)`, `register_enabled(features, feature_map, reg_id)`. The coordinator computes `self.features` once; platforms read features from the coordinator, not from the config entry directly.
- **When adding a register**: decide its feature tuple in the relevant `*_REGISTER_FEATURES` dict in `const.py`.
- **When adding a gated hand-written entity** (not register-driven, e.g. a switch built directly in `switch.py`): also add its unique_id suffix to `FEATURE_UNIQUE_ID_SUFFIXES` in `__init__.py`. `_remove_disabled_entities` uses that map to purge registry entries for disabled features on setup — miss it and the entity lingers as "unavailable" forever instead of disappearing.

## Gotchas

- `translations/en.json` must be kept as an exact copy of `strings.json`. Home Assistant loads `translations/` at runtime, not `strings.json` (that file is only for the HA developer-docs tooling) — editing one without the other silently desyncs the UI strings.
- The coordinator polls with block reads, not one request per register: `plan_reads` in `coordinator.py` groups the enabled addresses of each type (input, holding, coil) into spans, so a full poll is a handful of requests. Gated-off registers are skipped, but gaps of up to `MAX_READ_GAP` addresses are read through and discarded. If the device rejects a span, `_read_addresses` falls back to reading that span one address at a time (and warns once). Every enabled coil is polled, so coil switches show live state.
- Input registers 21-31 are the error history (active error plus previous ten), decoded by `error_codes.py` and shown by `GrantAerona3ErrorCodeSensor` and the Alarm Status sensor. Only the `L` letter is confirmed against real hardware; the other letters are inferred (see `Docs/error_codes.md`). If someone reports a code on the display that doesn't match, fix `LETTERS`/`LETTER_BASE` there rather than patching the sensors, and keep `Docs/error_codes.md` in step (it was generated from `ERROR_DESCRIPTIONS`).
- Don't pass `update_before_add=True` to `async_add_entities` for coordinator entities. `CoordinatorEntity.async_update` requests a coordinator refresh, so every entity added that way triggers an extra poll during setup (and another one after the debounce cooldown). Entities read `coordinator.data` when they're added, which the first refresh has already filled. `setup_times` in the HA diagnostics shows `wait_import_platforms` as a negative number: HA subtracts it, so the real setup time is `config_entry_setup` plus that value. The integration logs its own timing at the end of setup.
- Brand images live in `custom_components/grant_aerona3/brand/` (Home Assistant 2026.3+ serves them for custom integrations; older versions ignore them). They are generated by `Docs/brand/generate_brand.py` (Pillow only) from original artwork, not the manufacturer's logo, so edit the script and rerun it rather than editing the PNGs. Spec: PNG, transparent, trimmed; icon 256 and 512 px square; logo landscape with the short side 128-256 px (`@2x`: 256-512); `dark_` variants are optional.
- `diagnostics.py` backs the Download diagnostics button. It reads `coordinator.features`, `_enabled_addresses`, `_degraded_spans` and `last_poll_seconds`, so if you rename those, update it. Keep `TO_REDACT` covering anything that identifies the user's network or hardware (host, serial device path).
- A poll fails (`UpdateFailed`, entities go unavailable) when none of `CRITICAL_INPUT_REGISTERS` can be read; don't swallow that. The Communication Status binary sensor is the exception: it stays available and reads off when the last poll failed.
- `options_flow.py` was removed as dead code already — the options flow lives inside `config_flow.py`'s `OptionsFlowHandler`. Don't recreate a separate file for it.

## Flow offset and room trim (experimental, opt-in)

- Gated by the `experimental_flow_offset` feature (default OFF, deliberately unlike the hardware features), which also exists in `FEATURE_UNIQUE_ID_SUFFIXES`. The `climate` trim entity additionally needs the `room_trim_enabled` option and a sensor.
- `FlowOffsetManager` (`flow_offset_manager.py`) shifts Tm1/Tm2 (WC) or the fixed setpoint from a stored baseline. If the curve registers change outside the integration (two polls in a row), it adopts them as the new baseline and resets the offset. Keep `ZONE_FLOW_REGISTERS` in step with `HOLDING_REGISTER_MAP`. Te1/Te2 and cooling registers are deliberately never written.
- The pure logic (`flow_offset.py`, `flow_offset_manager.py`, `trim_controller.py`) imports nothing from Home Assistant so it can be tested with pytest: `.venv/bin/pytest tests` (create the venv with `python3 -m venv .venv && .venv/bin/pip install pytest`). Keep it that way.

## Validation

The pure flow-offset modules have pytest tests (above); the rest has no test suite or CI. Before committing, run the `validate` skill (or manually: `python3 -m py_compile` on every file in `custom_components/grant_aerona3/`, plus a JSON load check on `strings.json` and `translations/en.json`).
